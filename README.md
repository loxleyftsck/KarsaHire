# KarsaHire — Explainable AI Recruitment Copilot

KarsaHire is a local portfolio prototype for collaborative hiring teams. It helps recruiters and hiring managers agree on criteria, parse CVs, review evidence-backed matches, and keep a human-owned audit trail. See [the architecture plan](KarsaHire-Architecture-Plan.md) for the broader RAG, ranking, explainability, and governance design.

## Run locally

Continuing development in Antigravity or on another PC? Start with the [Antigravity handoff](ANTIGRAVITY_HANDOFF.md) for the current roadmap, verification limits, and next work.

Requires Python 3.10+. Parser dependencies and their runtime transitive dependencies are pinned in `requirements.txt`; upgrade those pins together and rerun the synthetic smoke suite before staging. From PowerShell, create an isolated project environment, install dependencies, and start the app:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe .\server.py
```

For the commands below, use `python` only when this virtual environment is active; otherwise invoke `.\.venv\Scripts\python.exe` as the interpreter.

Open <http://127.0.0.1:8765>. Select **Coba dengan data sintetis** for a sample requisition and built-in fictional CV, or create a requisition and load the bundled synthetic corpus after both approvals. Manual file uploads are disabled by default at both the UI and API. To exercise file parsing with synthetic fixtures on this loopback-only app, explicitly set `$env:RECRUITMENT_COPILOT_MANUAL_UPLOADS_ENABLED='true'` before starting `server.py`; the UI reads the setting from `/api/health`. Do not use real applicant CVs: the flag is only a local test switch and does not add authentication, authorization, or privacy approval. When enabled, text-based documents are parsed locally. PNG/JPG and scanned PDF pages are sent to the configured internal OCR API.

Local parser limits: 8 MB per upload; 1,000,000 total extracted characters and 20,000 nonempty lines per document across TXT, PDF, DOCX, and OCR output; 40 PDF pages; six embedded OCR images per PDF; six OCR requests per rolling minute; 40 megapixels per raster image; 32 MiB expanded/2,000 ZIP components per DOCX; and 1 MiB per OCR API response. Uploaded PNG/JPG bytes must match the filename extension. Request headers close after five seconds idle; request bodies must arrive within 60 seconds total with no more than five seconds idle. At most two upload/parse requests run at once in each server process; additional uploads receive HTTP 503 with Retry-After: 2 seconds. PDF parsing stops as soon as it encounters an image beyond its per-file limit. PDF files are parsed in a separate worker with a 256 MiB memory limit and 30-second deadline; pypdf output is capped at 2 MiB per decoded text stream, 8 MiB for image decoding, 32 MiB total normalized OCR images, and 48 MiB for the worker response. Windows applies a Job Object before sending PDF bytes; POSIX workers apply an address-space limit before importing the parser. The worker receives only runtime environment variables and does not inherit OCR credentials, endpoints, or proxy settings. TXT, DOCX, and direct image OCR parsing remain in the server process. These limits do not scan for malware or replace production host isolation and staged load validation.

The server defaults to port 8765 and accepts only a numeric port from 1 to 65535. Set `RECRUITMENT_COPILOT_PORT` before launching if that port is already occupied. SQLite defaults to `data/copilot.sqlite3`; set `RECRUITMENT_COPILOT_DB_PATH` to an absolute path before launching to keep the database outside the checkout. The parent folder is created when the app first opens the database, and the backup script uses the same configured path by default. Keep a protected database path and do not point multiple independent server processes at one file. The unauthenticated prototype always binds to `127.0.0.1`; setting `RECRUITMENT_COPILOT_HOST` to another address stops startup.

The repository includes a 32-record synthetic test corpus in `data/synthetic-cv-32`, sourced from [sukhrobnurali/resume-parsing-vision](https://huggingface.co/datasets/sukhrobnurali/resume-parsing-vision) (CC BY 4.0). Attribute the dataset to its source when redistributing it. The source dataset card states that the CVs are synthetic and contain no real personal data. To load them, create/select a requisition, record both approvals, then click **Muat CV uji (0/32)**. The loader imports local text references, calculates evidence scores locally, and does not call OCR. Re-importing the same dataset into the same requisition skips candidates already loaded. The source PDFs remain available for manual OCR testing.

For a local text-parser baseline against the corpus labels, run `python .\scripts\evaluate_synthetic.py`. It reads only manifest-scoped files inside the corpus directory and reports the parser version plus SHA-256 fingerprints for the manifest, consumed text/labels/metadata, and evaluator. It reports strict skill-label overlap, coverage of explicit experience-duration phrases, a small controlled duration-format probe, and literal education-label coverage plus mentions without a matching source label; career-duration metadata is not ground truth for explicit phrase extraction. Education overlap does not establish degree equivalency, authenticity, education level, or hiring relevance, and unmatched mentions are not confirmed errors because source labels may be incomplete. The strict precision/F1 values treat unmatched skill predictions as errors for the calculation only. Source labels may be incomplete, so these are not verified false-positive rates or parser quality metrics; recall covers only available in-vocabulary labels. This does not evaluate PDF extraction or OCR and is not evidence of hiring quality or fairness.

For a controlled TXT/DOCX/text-PDF consistency check, run `python .\scripts\evaluate_synthetic_formats.py`. It builds DOCX and single-column PDFs with wrapped text in memory from the same bundled synthetic text references and compares extracted text and profile fields. Synthetic probes also check paragraph/table order and row-wise two-column flattening, PDF page-number attribution, long evidence excerpts retaining matched/negated/partial terms within 700 characters, unscored evidence removed by redaction, recovery of a section heading merged after a sensitive label, and deterministic candidate-score ordering and tie breaks. The score-order probe is not a shortlist-quality benchmark. The PDF uses a printable-ASCII projection of each reference. Output records the parser `pipeline_version` plus SHA-256 fingerprints for the manifest, every consumed text reference, and evaluator source. A 32/32 match only shows round-trip consistency for those generated transformations; it does not establish accuracy on independently authored files, scanned PDFs, other languages, or hiring outcomes. The script prints aggregate counts, synthetic sample IDs, and reproducibility fingerprints only; it writes no files and makes no network requests.

For a targeted Windows OCR preprocessing probe, repeat `--sample-id` in `python .\scripts\evaluate_synthetic_ocr_preprocessing.py --sample-id r00196 --sample-id r00169 --sample-id r00344 --sample-id r00003 --language en-US`. It compares the original normalized PNG, grayscale/autocontrast, and 1.5× upscale/autocontrast on up to eight synthetic PDFs and emits aggregate WER only. It is diagnostic for the installed Windows OCR engine, not a provider selection or representative benchmark.

For an aggregate M2 reproducibility snapshot, run `python .\scripts\build_m2_reproducibility_report.py`. It runs the local text/format evaluators plus PDF and OCR preflights, records the exact pinned dependency versions and pipeline/evaluator/input fingerprints, and emits label-overlap, education, experience-duration coverage/probe, evidence-excerpt, format, PDF, and OCR-preflight aggregates only.

For a no-network PDF audit, run `python .\scripts\evaluate_synthetic_pdfs.py`. It reports which bundled synthetic PDF pages contain extractable text using pypdf only; it makes no OCR API requests and does not assess OCR quality.

For OCR evaluation preparation, run `python .\scripts\evaluate_synthetic_ocr.py --sample-id r00003`. This is preflight-only and sends nothing. Output records the parser `pipeline_version`, OCR model, and SHA-256 fingerprints for the dataset manifest, selected PDF, reference text, and evaluator. For a local no-network OCR run, install Tesseract and its English language data on the same machine using the [official installation guidance](https://tesseract-ocr.github.io/tessdoc/Installation.html), then run `python .\scripts\evaluate_synthetic_ocr.py --sample-id r00003 --local-tesseract --tesseract-language eng`. If the executable is not on `PATH`, add `--tesseract-executable "C:\Program Files\Tesseract-OCR\tesseract.exe"`. The script pipes only the selected synthetic PDF's normalized page images to the local Tesseract process and reports aggregate word error rate plus the Tesseract version; it does not print or persist OCR text. When an internal OCR key, URL, and approved-origin allowlist are configured, `--send-to-internal-ocr` remains a separate explicit network opt-in. The corpus reference is not adjudicated OCR ground truth, and neither path establishes OCR quality across layouts or languages.

The evaluator pins Tesseract to the discovered data prefix for the run; pass `--tesseract-tessdata-dir "C:\Program Files\Tesseract-OCR"` when the data directory is installed elsewhere. This helps distinguish model revisions but does not replace an adjudicated OCR benchmark.

For a local no-network Windows OCR probe, run `python .\scripts\evaluate_synthetic_ocr.py --sample-id r00003 --windows-ocr --windows-ocr-language en-US`. This uses the installed Windows.Media.Ocr engine and Windows PowerShell 5.1; select only a language tag already installed on that machine. The child process receives the normalized synthetic page image over standard input, and OCR output is used only in memory for aggregate WER. The report records the Windows build and bridge hash because Windows manages the OCR model and exposes no stable model fingerprint. One synthetic sample is a smoke result, not an OCR benchmark or evidence about the still-TBD pilot language.

For a corpus-wide local Windows OCR baseline, run `python .\scripts\evaluate_synthetic_ocr_corpus.py --language en-US`. It evaluates the pinned 32-PDF synthetic corpus without network access, rejects malformed/duplicate manifest IDs and incomplete image processing, verifies that the corpus and evaluator versions remain stable during the run, and emits per-sample aggregate WER plus corpus, input, runner, fingerprint-helper, and bridge hashes. It reports corpus WER only when every sample completes; partial runs retain per-sample diagnostics and omit corpus totals. It does not print or persist OCR text. The English synthetic corpus does not resolve the TBD M0 language or role; its reference text is not adjudicated ground truth.

## SQLite schema and local snapshots

The app tracks the SQLite schema with `PRAGMA user_version`. Startup applies numbered migrations in a transaction and refuses to open a database from a newer schema version. Migration v1 preserves existing requisitions and adds the original missing status column when needed. `/api/health/live` checks only whether the process can answer; `/api/health/ready` verifies the database responds and has the schema version this app supports, and returns HTTP 503 during shutdown drain. `/api/health` remains an alias for readiness and includes the pipeline version used by the evaluation worksheet plus the `manual_uploads_enabled` switch used by the UI. `/api/metrics` returns process-local uptime, request counts by method/route template/status, response bytes, active uploads, and upload backpressure count. Counters reset on restart and are not a replacement for a production metrics backend or alerts.

On `SIGINT` or `SIGTERM`, the process stays available for health probes during a five-second default drain window, rejects new application reads and writes with HTTP 503, then stops accepting requests and waits for active handlers. Set `RECRUITMENT_COPILOT_SHUTDOWN_GRACE_SECONDS` to an integer from 0 to 120 before startup to change the window. This is local process behavior and has not been validated with a load balancer.

To create a point-in-time backup while the app is running, run `python .\scripts\backup_database.py --output <protected-folder>\karsahire-snapshot.sqlite3`. The source opens read-only, SQLite's online backup API creates a consistent snapshot, `PRAGMA integrity_check` validates it, and publication refuses to overwrite an existing file. The command prints only metadata, not database rows. Backup and restore destinations inside the repository are rejected before folders are created, to reduce the chance that a database snapshot is committed to Git. To restore a snapshot into a new path without replacing an existing database, run `python .\scripts\restore_database.py --source <snapshot-file> --target <new-database-path>`. Restore validates integrity and refuses schema versions newer than this app, and prints a warning that a snapshot may reintroduce candidate data deleted after it was taken. Snapshots may contain applicant data: keep them outside the repository in an approved, access-controlled encrypted location. Deleting a candidate from the active database does not alter earlier snapshots; backup expiry/purge and deletion-aware restore handling remain pending M0/M4 decisions. Retention, managed storage, scheduled backups, secret protection, service cutover, and production restore approval are still M4 work. The smoke test restores only a synthetic fixture into a temporary database; it does not inspect or copy the local application database.

For a local restore-path switch, restore to a new file first, stop the app, set `RECRUITMENT_COPILOT_DB_PATH` to that file, restart, and check `/api/health/ready`. To roll back locally, stop the app and point the variable back to the previous database file. This documents a reversible local development procedure only; it has not been exercised in staging and does not establish production recovery readiness.

The [M4 local operations runbook draft](docs/operations/m4-local-runbook-draft.md) records startup, health checks, backup/restore, and incident steps. It is not an approved production runbook; owner, hosting, retention, alert, and cutover details remain to be supplied.

The [M5 local UAT checklist draft](docs/operations/m5-local-uat-checklist.md) prepares synthetic-only keyboard, chart, responsive, error, deletion, and audit checks. It has not been run with recruiter/hiring-manager participants and cannot satisfy M0, M2, M3, or M4 gates.

The local SQLite database and any OCR credentials are excluded from Git. A fresh checkout starts with an empty local database; run the app to create it.

## Database

KarsaHire uses SQLite at `data/copilot.sqlite3` by default. On startup, the server applies versioned, transactional migrations in `server.py`, creating missing tables and indexes without replacing existing records. [`database/schema.sql`](database/schema.sql) documents the base schema. The database file is local-only and excluded from Git.

| Table | Purpose |
|---|---|
| `jobs` | Requisitions, descriptions, criteria, and approval status |
| `approvals` | Recruiter and hiring-manager approvals for each requisition |
| `candidates` | Parsed profile summary, ranking score, and review status |
| `evidence` | Per-criterion match result, confidence, and CV snippet |
| `reviews` | Human reviewer decision and note |
| `audit_events` | Append-style record of workflow actions |

## Enable the internal OCR API

Before starting the server, provide the API key through `RECRUITMENT_COPILOT_OCR_API_KEY`, the OpenAI-compatible HTTPS base URL through `RECRUITMENT_COPILOT_OCR_API_URL`, and a comma-separated list of approved HTTPS origins through `RECRUITMENT_COPILOT_OCR_ALLOWED_ORIGINS` in the current process environment or an approved secret manager. The base URL's normalized origin (hostname and effective port) must exactly match one allowlisted origin; the allowlist accepts origins only, with no path, wildcard, credentials, query, or fragment. OCR fails closed if the allowlist is missing or does not match. The server rejects plaintext HTTP and base URLs containing user/password credentials, query strings, or fragments. Do not put credentials or internal service URLs in source files, command history, or the SQLite database. The model defaults to `ocr-lighton` and can be changed with `RECRUITMENT_COPILOT_OCR_MODEL`.

The OCR opener disables proxy discovery from environment variables and Windows system settings, and it rejects redirects. This prevents an unapproved ambient proxy route while M0/M3 owners decide the approved egress path; OCR will require a deliberate code/configuration change if that route requires a proxy. The origin allowlist validates the configured destination, but does not approve direct network egress, a proxy operator, or TLS inspection. The reviewed local environment has no OCR endpoint configured, and this behavior has not received runtime QC. See the [Python `urllib.request` documentation](https://docs.python.org/3.12/library/urllib.request.html#urllib.request.ProxyHandler).

The app sends each uploaded image or embedded scan page as an OpenAI-compatible `messages[].content` array containing text and a base64 `image_url`; it does not send `enable_thinking`. It enforces up to 6 embedded images per PDF, 6 OCR requests per rolling minute, a cap of 2 simultaneous upload/parse requests and 5 OCR client calls per local server process, and a 1 MiB response body cap per call. A scanned PDF with more than six embedded images is rejected before OCR requests are sent. OCR redirects and ambient proxy discovery are disabled; configure an approved final HTTPS endpoint so the API key stays scoped to that endpoint. These limits are local to this server process; they cannot count OCR calls made by other clients using the same key.

The OCR endpoint has not been called in the current environment because its key, URL, and approved-origin list are not configured. No real candidate CV has been sent. When enabled, OCR page images leave the local process and go to the configured API; the source file and full extracted CV text are not stored locally, but derived profile fields and matching evidence snippets are.

## Current behavior

- Stores requisitions, extracted skill/education/experience hints, evidence snippets, reviewer decisions, and audit events in local SQLite under `data/`. Common email/phone patterns and explicitly labeled direct identifiers or sensitive attributes in English and Indonesian are redacted from evidence and review notes before storage. This is heuristic and does not guarantee de-identification of unlabeled or unusual formats.
- Does not store the uploaded file, original filename, or full extracted CV text. Common contact fields are removed from evidence before persistence; this is a prototype safeguard, not a guarantee of complete de-identification.
- Gives each candidate an opaque ID. The score is a transparent lexical baseline: exact phrase evidence scores fully, partial token evidence scores partly, missing text is “unknown”, and direct English/Indonesian negation or conflicting mentions are “needs verification” with no score contribution. It is not an LLM ranking model and should not make hiring decisions; the negation check is a small heuristic, not comprehensive natural-language understanding.
- The requisition Q&A panel performs retrieval-only search over the saved description and approved criteria. It does not generate answers with an LLM; retrieved lines are shown as sources.
- Decisions (`advance`, `needs information`, `not selected`) are recorded only through an explicit human reviewer action.
- Approver names and roles are recorded separately, but are not authenticated; dual approval demonstrates the workflow and does not replace company SSO or authorization controls.
- Binds to `127.0.0.1`; this app has no authentication or production hardening and must not be exposed to a network.
- Adds browser security headers, a generic `Server: KarsaHire` response header without the Python runtime version, and accepts JSON API bodies only when `Content-Type` is `application/json` and the body is an object. These are local prototype safeguards, not a substitute for SSO, authorization, CSRF design, or a production security review.
- Requires every request to use a loopback `Host`; mutating API calls also need a same-origin `Origin` and the UI request marker. This blocks ordinary DNS-rebinding reads and cross-site form/fetch writes, but does not authenticate users or authorize local API clients.
- Writes JSON request logs to stdout with UTC time, a server-generated per-request correlation ID, method, route template, response status, and byte count. The ID is also returned in `X-Request-ID`; client-supplied IDs are ignored. Logs omit client IPs, raw URLs, candidate IDs, query parameters, and request headers. Production log collection, retention, access controls, and alerts remain M4 work.

## API outline

- `POST /api/jobs` — save a requisition and proposed criteria.
- `POST /api/jobs/{id}/approvals` — record separate recruiter and hiring-manager approvals; the app blocks CV processing until both roles sign off.
- `GET /api/jobs`, `GET /api/jobs/{id}` — list requisitions or view candidate evidence.
- `GET /api/health/live`, `GET /api/health/ready`, `GET /api/metrics` — process liveness, database readiness, and process-local operational counters.
- `POST /api/jobs/{id}/candidates` — parse a multipart TXT, PDF, DOCX, PNG, or JPG file.
- `POST /api/jobs/{id}/load-synthetic-data` — idempotently load the local 32-CV synthetic test set after criteria approval.
- `POST /api/jobs/{id}/ask` — retrieve relevant requisition text for an internal question.
- `POST /api/candidates/{id}/reviews` — record a human review.
- `DELETE /api/candidates/{id}` — delete a candidate and their evidence/reviews.
- `GET /api/jobs/{id}/events` — view the requisition audit trail.

Use synthetic or specifically authorized test data only. Before using real applicant data, replace the prototype safeguards with the approved company privacy, access-control, retention, audit, OCR, and fairness controls described in the architecture plan.
